# 거래처 주문·출고 v0.1 테스트·개발·배포 계획

## 1. 개발 순서

1. Starter Kit v0.1 기준점과 고객 전용 환경 확인
2. Prisma 모델·Enum·감사 action·마이그레이션 작성
3. 금액 계산, 상태 전환, 권한 정책 단위 테스트
4. 거래처·품목 기준정보 CRUD
5. 주문번호 생성과 주문 접수·수정·상세
6. 확인·확인 취소·취소·삭제·전체 출고 트랜잭션
7. 업무 현황과 검색·필터
8. Excel 다운로드
9. 공개 Demo seed·초기화 보호 장치
10. 브라우저 E2E, 동시 요청, 보안·시크릿 점검
11. 고객별 초기화·마이그레이션·배포 문서 검증

각 단계는 `lint`, `typecheck`, 관련 단위 테스트를 통과한 뒤 다음 단계로 이동한다. DB 변경은 커밋된 Prisma migration으로만 수행한다.

## 2. 단위 테스트

### 상태 전환

- `RECEIVED → CONFIRMED → SHIPPED` 정상 흐름
- `RECEIVED → CANCELLED`
- ADMIN의 `CONFIRMED → RECEIVED`
- USER의 확인 취소 차단
- 미확인 주문 출고 차단
- 출고·취소 주문 수정 및 삭제 차단
- 출고 완료 주문 재출고 차단

### 권한

- 비로그인 사용자 페이지·API 차단
- 비활성 계정 차단
- USER의 거래처·품목 변경 차단
- USER의 확인 주문 취소와 주문 삭제 차단
- ADMIN의 허용된 예외 처리
- UI에서 버튼을 숨겨도 직접 API 요청을 다시 차단

### 금액

- 수량 × 단가와 주문 합계
- 소수 수량과 금액 반올림
- 0 이하 수량, 음수 단가, 비정상 소수 자릿수 거부
- 클라이언트가 보낸 합계를 신뢰하지 않고 서버에서 재계산

### 삭제와 참조

- 주문 사용 이력이 있는 거래처·품목 삭제 차단
- 미사용 거래처·품목 ADMIN 삭제 허용
- `RECEIVED` 주문만 ADMIN 삭제 허용
- 확인 취소로 `RECEIVED`가 되었더라도 최초 확인 이력이 있으면 삭제 차단
- 삭제·취소 사유 누락 차단
- 삭제 후에도 감사 로그에 최소 식별 정보 유지

## 3. 통합·동시성 테스트

- 날짜별 주문번호가 중복되지 않음
- 동일 주문 확인 요청 2개 중 하나만 성공
- 동일 주문 출고 요청 2개 중 Shipment가 하나만 생성
- 상태 변경과 감사 로그가 함께 성공하거나 함께 rollback
- 비활성 거래처·품목은 신규 주문에서 선택 불가
- 기존 주문의 snapshot은 기준정보 수정 후에도 유지
- 필터 조건과 Excel 결과 건수 일치

## 4. Playwright 브라우저 E2E

### ADMIN 시나리오

1. 로그인
2. 거래처·품목 생성
3. 주문 접수 및 금액 확인
4. 주문 확인
5. 확인 취소 후 수정
6. 재확인 및 출고
7. 업무 현황·최근 활동 확인
8. Excel 다운로드와 파일 헤더 확인
9. 로그아웃 후 보호 페이지 차단 확인

### USER 시나리오

1. 로그인
2. 거래처·품목 조회
3. 주문 접수·수정·확인·출고
4. 거래처·품목 변경 API 403 확인
5. 확인 취소·확인 주문 취소·삭제 API 403 확인
6. 검색과 Excel 다운로드 확인

### 오류 시나리오

- 필수값, 수량, 단가 입력 검증
- 잘못된 상태 순서 차단
- 이미 처리된 화면에서 재요청했을 때 충돌 응답
- 없는 ID와 타 도메인 ID 접근 시 안전한 오류

E2E 데이터는 `.invalid` 계정, 고유 prefix의 거래처·품목·주문만 사용하고 테스트 전후에 관련 감사 로그까지 정리한다. 실제 관리자 계정과 고객 데이터는 사용하지 않는다.

## 5. 공개 Demo 운영

- Demo는 고객 환경과 다른 DB·시크릿·배포 식별자를 사용한다.
- seed 데이터는 현실적인 가상 거래처·품목·주문만 포함한다.
- 실제 회사명, 전화번호, 이메일, 사업자번호를 포함하지 않는다.
- 방문자 계정은 USER 권한으로 업무 흐름을 체험한다.
- 사용자 관리와 보안 설정 Route는 Demo 방문자에게도 기존 권한 규칙대로 차단한다.
- 매일 초기화하며 실행 전 `DEMO_MODE=true`와 Demo DB 식별자를 모두 검증한다.
- 초기화 작업은 업무 테이블과 Demo 감사 로그만 대상으로 하며 Core 관리자 계정은 별도 보호한다.
- Demo 초기화 실패는 기존 데이터를 삭제한 채 계속 진행하지 않고 실패 상태를 알린다.

## 6. 고객별 복제·배포 원칙

- 고객마다 독립 디렉터리 또는 저장소, DB, Compose 프로젝트, 볼륨, 네트워크, 포트를 사용한다.
- `AUTH_SECRET`, DB 비밀번호, 최초 관리자 자격정보는 환경과 고객 사이에서 공유하지 않는다.
- `.env.example`에는 키와 비민감 예시만 두고 실제 값은 Git에서 제외한다.
- 신규 고객은 빈 DB에 `prisma migrate deploy`를 실행한 뒤 최초 관리자를 생성한다.
- Preview와 테스트 환경은 운영 DB를 참조하지 않는다.
- 마이그레이션 전 백업·복구 가능 여부를 확인한다.
- 고객별 기능 차이는 Core를 수정하기보다 업무 모듈 설정과 별도 커밋으로 관리한다.

## 7. 완료 기준

- 합의된 포함 기능이 모두 구현되고 제외 기능이 유입되지 않음
- 페이지·API·서비스의 권한 검증 통과
- 모든 상태 전환과 예외 처리의 감사 로그 확인
- lint, typecheck, 단위·통합·Playwright E2E, production build 통과
- 테스트 데이터 0건 확인
- 실제 시크릿과 개인정보가 Git·로그·Excel fixture에 없음
- Demo와 고객 DB의 물리적 분리 확인
- README와 `docs/`가 실제 명령·화면·API와 일치

## 8. 주요 위험과 후속 범위

- 공유 Demo는 방문자 간 데이터가 보일 수 있으므로 반드시 가상 데이터만 사용한다.
- 대량 Excel은 메모리를 사용할 수 있어 행 수 제한이 필요하다.
- 부분 출고 요구가 생기면 Shipment와 품목별 출고 수량 모델을 별도 버전에서 재설계한다.
- 재고·정산·외부 연동은 현재 모델에 임시 필드를 추가하지 않고 후속 요구사항으로 분리한다.
- DB 장애 시 best-effort 인증 감사 로그가 누락될 수 있는 기존 Core 위험은 유지된다.
