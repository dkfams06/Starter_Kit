# 주문·출고 v0.1 운영·검증 안내

## 구현 범위

Core 인증·사용자·Task를 유지하고 `src/modules/order-shipping`에 업무 로직을 분리했다.
거래처/품목 → 주문 접수 → 확인 → 전체 출고 → 검색/Excel이 구현 범위다.
재고, 부분 출고, 세금, 정산, 결제, 외부 연동은 포함하지 않는다.

USER는 기준정보를 조회하고 주문 접수·수정·확인·전체 출고·접수 취소·Excel을 사용한다.
ADMIN만 기준정보 변경, 확인 취소, 확인 주문 취소, 확인 이력 없는 접수 주문 삭제가 가능하다.
비활성 계정은 페이지/API에서 차단한다. 내부 서비스도 역할·상태를 검증한다.

모든 주문 변경은 현재 `version`을 요구한다. 409이면 페이지를 새로고침하고 내용을 재확인한다.
출고·취소 주문은 수정할 수 없으며 출고는 되돌릴 수 없다. 확인 취소로 접수 상태가 되어도
최초 확인 이력이 있으면 영구 삭제할 수 없다. 삭제·취소·확인 취소에는 사유가 필요하다.
스냅샷은 기준정보 수정과 분리되며 같은 거래처/품목을 유지한 주문 수정에도 보존한다.
기존 주문에 이미 포함된 비활성 기준정보는 유지할 수 있지만 새로 선택할 수 없다.

## 데이터와 Excel

- 주문일과 날짜별 번호는 서버가 생성하며 업무일은 Asia/Seoul 기준이다.
- 수량 numeric(14,3), 단가 numeric(14,2), 금액 numeric(16,2). DB와 서버 양쪽에 범위 검증이 있다.
- 주문별 최대 50품목, 목록 20건, 선택 옵션 최대 500개, Excel 최대 5,000품목 행.
- Excel은 실제 `.xlsx`이며 현재 검색 조건을 적용한다. 품목별 한 행으로 저장한다.
- 문자열은 수식이 아닌 텍스트로 저장하고 수식 모양 접두어도 escape한다.
- 다운로드는 감사 로그에 행 수만 남긴다. 계정 이메일·비밀번호·키는 내보내지 않는다.
- Excel의 숫자 표현은 15자리 정밀도 제약이 있으므로 매우 큰 금액의 최종 기준은 DB다.

## 전용 데모 운영

고객 DB와 시크릿을 공유하지 않는다. 실제 회사명·주소·연락처를 넣지 않는다.
공개 방문자와 가입자는 공유 USER 환경이며 다른 방문자의 업무 데이터를 볼 수 있다.
초기화는 UI/API에 노출하지 않고 배포 운영자의 CLI로만 실행한다.

먼저 실제 `.env`/`.env.local`의 연결 대상이 **전용 데모 DB**인지 확인한다.
`DEMO_MODE=true`, `DEMO_DATABASE_NAME`, `DEMO_DATABASE_HOST`를 명시한다.
CLI는 연결 URL의 host/name과 접속 DB의 `current_database()`를 비교한다.

```bash
# 아래 식별자는 이 로컬 데모 전용 예시다. 고객 DB에서는 실행 금지.
DEMO_DATABASE_NAME=starterkit DEMO_DATABASE_HOST=127.0.0.1 pnpm demo:preview
DEMO_DATABASE_NAME=starterkit DEMO_DATABASE_HOST=127.0.0.1 pnpm demo:seed
```

`demo:preview`는 변경 없이 개수만 확인한다. `demo:seed`는 접수·확인·출고 샘플을
고정 식별자로 추가하며 기존 샘플을 덮어쓰지 않는다. 수정/삭제된 샘플의 원상복원은 reset으로 한다.

초기화 직전에는 접근 제한된 위치에 DB 백업을 저장하고 복원 가능 여부를 확인한다.
다음 명령은 **해당 전용 데모 DB의 모든 거래처·품목·주문·출고와 업무 감사 로그를 삭제**하고
샘플을 재생성한다. 개별 방문자 입력만 골라 지우는 명령이 아니다.

```bash
DEMO_DATABASE_NAME=starterkit DEMO_DATABASE_HOST=127.0.0.1 \
DEMO_RESET_CONFIRM=RESET:starterkit pnpm demo:reset
```

- Core 사용자(관리자 포함), Task, 인증 감사 로그, 기존 DEMO_RESET 로그, 주문번호 카운터는 보존한다.
- 삭제와 샘플 재생성은 한 트랜잭션이다. 실패하면 전부 롤백한다.
- 초기화는 배타적 advisory lock, 일반 업무 변경은 공유 lock을 사용한다.
- 삭제된 업무 데이터의 복구는 별도 백업이 있어야 가능하다.
- 매일 실행하려면 전용 배포의 스케줄러에 위 명령을 1회 등록한다. 이 작업에서 호스트 cron이나 외부 자동화는 등록하지 않았다.
- 스케줄러는 작업 디렉터리·환경변수·실행 계정을 명시하고 실패 시 운영자에게 알리도록 설정한다. 동일 DB에서 중복 스케줄을 만들지 않는다.

## 검증 명령

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm test:e2e:browser
DEMO_DATABASE_NAME=starterkit DEMO_DATABASE_HOST=127.0.0.1 pnpm exec tsx scripts/test-demo-reset.ts
```

마지막 명령은 초기화를 트랜잭션 안에서 검증하고 의도적으로 롤백한다. Core 보존과
실행 전후 개수 일치를 검사하며 영구 초기화는 수행하지 않는다. 다른 쓰기 작업이 없는
전용 테스트/데모 환경에서 실행한다. 테스트 실패 때도 롤백하며 다른 DB에는 실행하지 않는다.

브라우저 테스트는 ADMIN 주문 접수·확인·확인 취소·수정·출고·파일 다운로드, USER 권한,
버전 충돌, 동시 확인/출고, 번호 중복 방지, 스냅샷·삭제 제한·감사 로그를 검증한다.
테스트용 계정/거래처/품목/주문은 고유 식별자로 정리한다. 주문번호에 테스트로 인한 빈 번호는 남는다.

## 신규 고객 배포

README의 신규 고객 초기화 절차를 따른다. 이 작업에서 고객 DB나 배포는 새로 만들지 않았다.

1. 독립 경로/저장소, main, 고유 Compose 리소스 이름·포트를 준비한다.
2. `.env.example`만 복사하고 새 DB 비밀번호와 AUTH_SECRET을 생성한다. DEMO_MODE=false로 둔다.
3. 의존성 설치 → 빈 DB에 `pnpm db:deploy` → `pnpm db:generate` → 최초 ADMIN 생성 순서로 진행한다.
4. 전용 테스트 DB에서 검증 후 빌드하고 실제 origin과 AUTH_URL을 일치시킨다.
5. 기존 고객 업그레이드는 백업/복원 점검 후 커밋된 migration만 적용한다. `migrate reset`은 사용하지 않는다.
6. 인터넷 공개 시 HTTPS·요청 제한·모니터링·백업 정책을 별도로 구성한다.

## 남은 운영 위험

- 공유 데모는 방문자별 격리가 없으며 입력량·다운로드 남용에 대한 인프라 요청 제한이 필요하다.
- 일일 초기화 스케줄·실패 알림과 실제 외부 배포는 미설정이다.
- 이메일 확인/비밀번호 복구는 범위 밖이다. 초기화가 가입 계정까지 지우지는 않는다.
- 기준정보 선택 UI 500건 한도를 넘는 고객은 검색형 선택을 추가해야 한다.
- 기존 Core 인증 감사는 DB 장애 시 best-effort 기록이 누락될 수 있다.
- 2026-10-11 `pnpm audit --prod` 결과: 기존 Prisma 하위 의존성 `deepmerge-ts`, `mysql2`에 high 2건·moderate 1건이 남는다. 앱 DB는 PostgreSQL이지만 의존성 경고 자체가 해결된 것은 아니다. 메이저 Prisma 변경은 별도 호환성 검증 작업으로 분리한다. 인터넷 공개 전 의존성 경고를 재점검한다.
- 신규 ExcelJS 경로의 uuid 경고는 `exceljs>uuid=11.1.1` override로 제거하고 xlsx 생성/읽기 테스트로 호환성을 확인한다. ExcelJS는 서버에서만 사용한다.
