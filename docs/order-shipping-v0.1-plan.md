# 거래처 주문·출고 관리 시스템 v0.1 기획

## 1. 문서 상태

- 기준 Core: Starter Kit v0.1, commit `7f27d2b`
- 제품 성격: 중소 도소매·유통업을 예시로 한 범용 B2B 내부 운영 시스템
- 핵심 가치: 경영 분석보다 주문 처리의 정확성, 상태 통제, 담당자 추적
- 배포 방식: 고객사별 독립 애플리케이션·DB·시크릿을 사용하는 single-tenant 배포
- 공개 방식: 실제 고객 환경과 분리된 공개 Demo 배포

## 2. 사용자와 목표

실제 제품 사용자는 고객사 내부 직원이다. 외부 거래처가 로그인하거나 직접 주문하는 포털은 v0.1에 포함하지 않는다.

사용자는 다음 질문에 빠르게 답할 수 있어야 한다.

- 어떤 거래처에서 어떤 품목을 얼마나 주문했는가?
- 주문이 접수, 확인, 출고 중 어느 단계에 있는가?
- 누가 언제 주문을 확인하거나 출고했는가?
- 지정 기간과 조건의 주문을 Excel로 내려받을 수 있는가?

## 4. 업무 흐름

정상 흐름은 반드시 다음 순서를 따른다.

```text
RECEIVED(접수) → CONFIRMED(확인) → SHIPPED(전체 출고)
       │                │
       └─ 취소          ├─ ADMIN 확인 취소 → RECEIVED
                        └─ ADMIN 취소
```

### 상태 규칙

| 현재 상태 | 허용 작업 | 다음 상태 |
|---|---|---|
| `RECEIVED` | 주문 내용 수정 | `RECEIVED` |
| `RECEIVED` | 주문 확인 | `CONFIRMED` |
| `RECEIVED` | 주문 취소 | `CANCELLED` |
| `RECEIVED` | ADMIN 오입력 삭제(확인 이력 없음) | 삭제 |
| `CONFIRMED` | 전체 출고 | `SHIPPED` |
| `CONFIRMED` | ADMIN 확인 취소 | `RECEIVED` |
| `CONFIRMED` | ADMIN 주문 취소 | `CANCELLED` |
| `SHIPPED` | 조회만 가능 | 변경 없음 |
| `CANCELLED` | 조회만 가능 | 변경 없음 |

- 확인하지 않은 주문은 출고할 수 없다.
- 출고는 주문 전체에 대해 한 번만 처리한다.
- 취소, 확인 취소, 삭제에는 사유가 필요하다.
- 확인 이후의 일반 필드 수정은 금지한다.
- 상태 전환과 감사 로그 기록은 같은 DB 트랜잭션으로 처리한다.
- 동시에 같은 주문을 처리해도 확인·출고가 중복되지 않아야 한다.

## 5. 권한

| 기능 | USER | ADMIN |
|---|:---:|:---:|
| 거래처·품목 조회 | O | O |
| 거래처·품목 등록·수정·비활성화 | X | O |
| 사용 이력 없는 거래처·품목 삭제 | X | O |
| 주문 접수·조회 | O | O |
| 접수 상태 주문 수정 | O | O |
| 주문 확인 | O | O |
| 접수 상태 주문 취소 | O | O |
| 확인 상태 주문 취소 | X | O |
| 주문 확인 취소 | X | O |
| 주문 전체 출고 | O | O |
| 확인 이력 없는 접수 상태 오입력 주문 삭제 | X | O |
| Excel 다운로드 | O | O |
| 사용자·감사 로그 관리 | X | O |

페이지 메뉴 숨김만으로 권한을 판단하지 않는다. 페이지, Route Handler, 업무 서비스의 DB 접근 직전까지 역할과 활성 상태를 검증한다.

## 6. 삭제와 보존 정책

- 거래처·품목은 주문 사용 이력이 있으면 삭제하지 않고 비활성화한다.
- 사용 이력이 없는 거래처·품목만 ADMIN이 삭제할 수 있다.
- 주문은 `RECEIVED` 상태이면서 확인 이력이 없을 때만 ADMIN이 오입력 삭제할 수 있다.
- 한 번이라도 확인된 주문과 출고된 주문은 영구 삭제할 수 없다.
- 주문 삭제 시 주문번호, 거래처, 삭제자, 삭제 사유를 감사 로그에 보존한다.
- 장기 데이터는 삭제가 아니라 연도별 백업·보관으로 관리하며 보관 자동화는 v0.1 범위 밖이다.

| 경로 | 화면 | 주요 기능 |
|---|---|---|
| `/admin/operations` | 업무 현황 | 오늘 접수, 확인 대기, 출고 대기, 오늘 출고, 최근 활동 |
| `/admin/customers` | 거래처 목록 | 검색, 활성 상태 필터, 등록 진입 |
| `/admin/customers/new` | 거래처 등록 | 거래처 기본정보 입력 |
| `/admin/customers/[id]` | 거래처 상세 | 조회, ADMIN 수정·비활성화·제한 삭제 |
| `/admin/products` | 품목 목록 | 검색, 활성 상태 필터, 등록 진입 |
| `/admin/products/new` | 품목 등록 | 코드, 명칭, 규격, 단위, 기준 단가 입력 |
| `/admin/products/[id]` | 품목 상세 | 조회, ADMIN 수정·비활성화·제한 삭제 |
| `/admin/orders` | 주문 목록 | 기간·상태·거래처·주문번호 검색, Excel 다운로드 |
| `/admin/orders/new` | 주문 접수 | 거래처 선택, 주문 품목 편집, 금액 계산 |
| `/admin/orders/[id]` | 주문 상세 | 상태별 수정·확인·취소·출고·이력 조회 |

### 화면 원칙

- 목록은 기존 `DataTable`, 빈 데이터·로딩·오류 상태를 재사용한다.
- 단순 기준정보는 공통 Form Dialog를 사용할 수 있다.
- 주문 접수는 복수 품목과 금액 확인이 필요하므로 독립 페이지로 만든다.
- 위험 작업은 확인 Dialog와 사유 입력을 요구한다.
- 모바일에서는 조회와 상태 처리를 지원하되 대량 주문 입력은 데스크톱을 우선한다.

## 8. 공개 Demo

- 실제 고객 환경과 별도 배포·DB·시크릿을 사용한다.
- 방문자는 안내된 DEMO 계정으로 로그인한다.
- DEMO 사용자는 주문 접수, 확인, 출고, 조회, Excel을 체험할 수 있다.
- 사용자 관리, 비밀번호 변경, 보안 설정, Demo 초기화 기능은 방문자에게 제공하지 않는다.
- 샘플 거래처·품목·주문을 제공한다.
- Demo 업무 데이터는 매일 자동 초기화하며 ADMIN은 필요 시 수동 초기화할 수 있다.
- 초기화 로직은 `DEMO_MODE`가 명시된 Demo 환경에서만 실행되도록 보호한다.
